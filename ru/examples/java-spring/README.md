# Пример интеграции Telegram на Java и Spring Boot

**Статус:** локальный пример; аккаунт Telegram не подключён, сообщения не отправлялись.

В проекте есть пятнадцать шаблонов:

1. Webhook Bot API с проверкой секретного заголовка, небольшим списком команд и выключенной по умолчанию отправкой.
2. Работающая форма Telegram Mini App с серверной проверкой `initData`, проверкой владельца при получении статуса и синтетическими данными.
3. Синтетическое групповое голосование за время через inline-кнопки, серверный список разрешённых участников и защиту от повторной обработки callback.
4. Адаптер Jira Cloud webhook с проверкой подписи, фильтрацией событий и минимальным Telegram-уведомлением.
5. Подписанный Grafana Alerting webhook с кнопкой прикладного подтверждения для разрешённых пользователей.
6. Приём текстовых файлов через Bot API только с согласием пользователя, приватной временной директорией и немедленным удалением.
7. Необязательный сценарий Claude Messages API для вопроса, отправленного напрямую в личный чат: раскрытие обработки, согласие на функцию и отдельное подтверждение каждого точного запроса.
8. Смоделированный приём Telegram Business: права подключения, новые/изменённые/удалённые сообщения, минимальная тестовая заявка, передача разрешённому оператору и проверка соединения, `can_reply` и 24-часового окна до ответа с `business_connection_id`.
9. Сбор заявки клиента с отдельным согласием: поля из личного чата upsert-ятся в HubSpot по email, назначаются настроенному владельцу CRM, а менеджер получает только ссылку-идентификатор записи.
10. Приватный процесс внутренних заявок: server-side справочник ролей сотрудника/менеджера, просмотр статуса, подтверждение решения двумя callback-действиями, защита от устаревшего действия и минимальный аудит в UTC.
11. Локальный H2 outbox уведомлений с устойчивыми event ID, lease для задач worker, ограниченными повторами, обработкой `retry_after`, сроком годности и очисткой terminal-записей.
12. Mock-шов передачи поддержки в Chatwoot: синтетическое назначение диалога, ответы назначенного оператора из allowlist и fake gateway. Встроенный канал Telegram в Chatwoot остаётся самой Telegram-интеграцией; этот Java-шов не содержит HTTP-клиента, webhook endpoint или постоянного хранилища.
13. Общая доска доступности Mini App с подписанным контекстом запуска из группы, точным allowlist пары «чат/пользователь», пользовательскими слотами, агрегированными счётчиками, безопасными повторами и конфликтами версий.
14. Синтетический цикл Telegram Stars: приватное создание локального заказа, проверка pre-checkout, выдача синтетического права только после успешного платежа, защита от повторов, возврат только владельцем и справка по оплате. Fake-адаптер работает только в памяти: он не создаёт invoice, не обращается к Telegram и не перемещает Stars.
15. Необязательный пример Telegram Login OIDC для обычного сайта на Spring Security: Authorization Code с PKCE, серверные `state`/`nonce`, минимальный scope `openid` и ответ только с идентификатором subject. Это отдельный сценарий, не связанный с проверкой Mini App `initData`; по умолчанию он выключен.

Примеры объединены в одном приложении, чтобы были видны границы данных. В репозитории нет секретов, живых тестовых данных, индексирования истории, TDLib или реальной отправки. Приём файлов реализован в этом Spring-примере; отдельный [необязательный Java-пример TDLib](../tdlib-java/README.md) не входит в старт Spring и требует явной настройки native/JNI. См. [обзор задач](../../tasks/1.md).

## Требования

- Java 25
- Доступ к сети нужен только для загрузки Gradle и зависимостей
- Для локального старта и dry-run webhook не нужны токены Telegram или Claude

## Локальный запуск

```bash
./gradlew bootRun --args='--spring.profiles.active=demo'
```

Запустить автоматические тесты без учётных данных:

```bash
./gradlew test
```

Тесты используют синтетические данные и внедряемый HTTP-транспорт. Они не подключаются к Telegram или AI-провайдеру. `JdkHttpTransport` — рабочий адаптер; в unit-тестах он заменяется внутрипроцессной заглушкой.

Из корня репозитория можно проверить отслеживаемые и неигнорируемые файлы на распространённые форматы Telegram- и AI-секретов:

```bash
bash scripts/credential-scan.sh
```

Это проверка по ограниченному набору шаблонов, а не гарантия обнаружения секретов любого формата. Сырые Telegram updates храните вне репозитория: каталог `telegram-updates/` и файлы с окончанием `.telegram-update.json` игнорируются Git.

Для отправки используется Java `HttpClient`. В тестах базовый URL API направлен на встроенный локальный HTTP-сервер; по умолчанию задан официальный адрес Telegram. Пример не повторяет отправку автоматически: при HTTP 429 в рабочей очереди следует учитывать `retry_after` из Bot API и использовать ограниченную задержку, поскольку слепой повтор может создать дубликат. Bot API-бот — отдельный аккаунт, который не может искать произвольную историю пользовательских чатов; пользователь должен открыть бота или добавить его в разрешённый чат.

## Уведомления из GitHub Actions

Workflow `.github/workflows/java-sample-ci.yml` запускает тесты Java-примера для pull request, но намеренно не выполняет Telegram-шаги ни для одного pull request. При push в `master` и ручном запуске на `master` он сообщает итоговый статус workflow и ссылку на его страницу. Без настроек остаётся dry-run. Чтобы включить отправку позже, добавьте `TELEGRAM_BOT_TOKEN` в GitHub Actions secrets, а `TELEGRAM_CHAT_ID` — в repository variables; пользователь должен сначала открыть бота или добавить его в разрешённую группу. Значений в репозитории нет. Fork pull request не получает секрет. Workflow имеет только разрешение `contents: read`.

Уведомление использует HTML с экранированием динамических значений и не включает логи. Форматирование можно посмотреть без секретов:

```bash
CI_JOB_STATUS=failure GITHUB_REPOSITORY=demo/project GITHUB_REF_NAME='feature/<test>' GITHUB_SHA=0123456789abcdef GITHUB_SERVER_URL=https://github.com GITHUB_RUN_ID=123 TELEGRAM_SEND_ENABLED=false ./gradlew -q notifyTelegram
```

Команда выведет dry-run маркер без текста сообщения. Форматтер и режим отправки CI-уведомления покрыты тестами без секретов; локальные тесты не обращаются к чату. Не используйте `pull_request_target`, чтобы запускать недоверенный код с Telegram-секретами.

## Пример группового голосования

В группе или супергруппе команда `/vote` публикует синтетический вопрос о времени обслуживания с inline-кнопками. Задайте `TELEGRAM_ALLOWED_VOTER_IDS` в окружении процесса как список числовых ID пользователей Telegram через запятую; пустое значение запрещает все голоса. Для каждого callback сервер сверяет ID отправителя из проверенного webhook update со списком. Создатель голосования может завершить его командой `/closevote <vote-id>`. У пользователя хранится один текущий выбор, который можно изменить; повторная доставка update не добавляет второй голос. Сообщение редактируется с текущими итогами, а создатель может опубликовать финальный результат.

Демо хранит в памяти до 1 000 голосований. После перезапуска они пропадают и не разделяются между экземплярами; для production нужны общее долговременное хранилище и проверка прав с учётом реальных групповых или бизнес-ролей. Не коммитьте настоящие ID пользователей. При включённом privacy mode Telegram передаёт боту команды и ответы, относящиеся к нему, а не произвольные сообщения группы; этот пример не читает историю. Для простого голосования без специальных прав лучше использовать встроенный `sendPoll`; inline-кнопки уместны здесь, потому что приложению нужны проверка каждого пользователя и собственное изменяемое состояние. Локальные тесты используют синтетические updates и внутрипроцессный HTTP-сервер; реальные сообщения в группу не отправляются.

## Пример Jira Cloud webhook

Java endpoint `POST /jira/webhook` принимает типы событий `jira:issue_created` и `jira:issue_updated`. В админке Jira Cloud настройте эти события и задайте стойкий секрет webhook. Jira подписывает точное UTF-8 тело запроса в `X-Hub-Signature` в формате `sha256=<hex>`; пример проверяет подпись с constant-time сравнением и отклоняет запросы без корректной подписи. Для устранения повторов требуется `X-Atlassian-Webhook-Identifier`, который Jira документирует как одинаковый для повторных попыток доставки. Jira Cloud повторяет неудачные запросы и может доставлять события несколько раз. Адаптер читает проект, тип задачи, summary, статус и changelog статуса, затем применяет настроенные фильтры по проекту, необязательным типам задачи и конечным статусам. Telegram-сообщение содержит только ключ задачи, экранированный summary, тип события/статус и ссылку; описание, комментарии и весь payload не пересылаются.

Общий servlet filter считывает не более 1 000 001 байта до привязки тела в Spring; запросы больше 1 MB получают HTTP 413, в том числе без `Content-Length`. Обёртка сохраняет точные исходные байты для HMAC-проверки. Контроллер оставляет дополнительную проверку размера.

Для локального запуска выполните `./gradlew test`: синтетические payload, HMAC и Telegram-клиент работают локально. Пример обслуживает один Jira tenant и хранит до 10 000 ID событий в памяти; после перезапуска записи теряются. В production нужна общая долговременная дедупликация (для нескольких сайтов ключ должен включать tenant ID). Приём ограничен телом в 1 MB, хотя Jira описывает больший максимум для доставки. В этом небольшом примере обработка синхронная; в production нужно быстро подтверждать webhook и передавать работу в долговременную очередь/outbox, чтобы переживать всплески и не расходовать время на повторы Jira из-за задержки Telegram. Jira требует HTTPS URL с TLS-сертификатом от общедоверенного центра; для production также учитывайте опубликованные Atlassian IP-диапазоны исходящих подключений. В этом проекте не создавалась Jira-конфигурация, публичный endpoint, Telegram token или chat ID, реальные сообщения не отправлялись.

Для контролируемого развёртывания используются переменные `JIRA_WEBHOOK_SECRET`, `JIRA_PROJECT_KEY`, `JIRA_TELEGRAM_CHAT_ID` и `JIRA_BASE_URL`; необязательные фильтры задаются через `JIRA_ISSUE_TYPES` и `JIRA_DESTINATION_STATUSES` списками через запятую. Для реальной отправки Telegram дополнительно потребуются `TELEGRAM_BOT_TOKEN` и `TELEGRAM_SEND_ENABLED=true`; по умолчанию отправка выключена. Секрет подписи Jira отделён от `TELEGRAM_WEBHOOK_SECRET`.

Названия событий Jira, поля issue/changelog, формат HMAC, требование HTTPS и ID повторной доставки проверены по [документации Atlassian Jira Cloud webhooks](https://developer.atlassian.com/cloud/jira/platform/webhooks/) 2026-11-15. Документация позволяет фильтровать события и поля при регистрации webhook; в примере те же фильтры повторяются на сервере как дополнительная проверка. Сейчас валидатор принимает только `sha256`; Atlassian отмечает, что алгоритм подписи может измениться, поэтому валидатор нужно обновить при смене метода.

## Grafana Alerting webhook и подтверждение

В Grafana уже есть встроенный Telegram contact point для отправки уведомлений без дополнительных действий. Используйте его, если достаточно простой маршрутизации. Java-адаптер нужен, если команде требуются собственная фильтрация, запись приложения и явное подтверждение человеком. Webhook contact point Grafana отправляет JSON-объект с `status`, массивом `alerts[]` и полями alert, включая `labels`, `startsAt`, `generatorURL` и `fingerprint`. Пример публикует отдельное краткое сообщение для каждого alert (не более 10 на payload): `alertname`, `severity`, выбранные labels `team`/`service`/`environment`, состояние firing/resolved и проверенную ссылку на источник. Annotations, остальные labels, значения и полный payload не отправляются.

Endpoint `/grafana/webhook` требует секрет, подпись HMAC-SHA256 и timestamp. В Grafana задайте HMAC signature с заголовком `X-Grafana-Alerting-Signature`, timestamp header `X-Grafana-Timestamp` и секретом `GRAFANA_WEBHOOK_SECRET`. Подпись должна совпасть с `HMAC-SHA256(secret, timestamp + ":" + rawBody)`; timestamp старше или более чем на пять минут в будущем будет отклонён. Пять минут — политика этого примера. Тело запроса ограничено 1 MB.

Общий servlet filter применяет лимит 1 MB до привязки тела запроса в Spring и сохраняет исходные байты для проверки подписи; он также ограничивает запросы без `Content-Length`. Контроллер повторно проверяет размер после привязки.

В Telegram-сообщении есть inline-кнопка **Acknowledge**. Добавьте `callback_query` в `allowed_updates` webhook бота и задайте `GRAFANA_ACK_USER_IDS` как список разрешённых Telegram ID через запятую. Пустой список запрещает подтверждения всем. Успешное действие записывает ID пользователя и время UTC в ограниченное in-memory хранилище приложения и редактирует сообщение. Повторные нажатия идемпотентны. Это не подтверждает, не разрешает и не ставит Grafana alert на паузу и не вызывает Grafana API. Действие работает только в настроенном Telegram-чате. У бота должно быть право отправлять сообщения в этот чат; история переписки не читается.

Хранилище подтверждений ограничено 1 000 экземплярами alert и очищается при перезапуске; для production нужны общее долговременное хранилище и политика аудита/срока хранения. У Grafana webhook в примере нет стабильного ID доставки, поэтому повторные уведомления, настроенные в Grafana, могут создавать ещё одно сообщение. Настройте количество alert в payload и частоту уведомлений с учётом рабочего чата. Отправка Telegram остаётся выключенной, пока её явно не включат через переменную окружения.

Локальная проверка использует синтетические firing/resolved payload, тестовые подписи и подменный Telegram-клиент. Реальные Grafana, публичный contact point, Telegram-аккаунт или сообщение не использовались. Для живого подключения нужны HTTPS endpoint Java, доступный Grafana, contact point Grafana с HMAC/timestamp, `GRAFANA_WEBHOOK_SECRET`, `GRAFANA_TELEGRAM_CHAT_ID`, `GRAFANA_ACK_USER_IDS`, `TELEGRAM_BOT_TOKEN` и отдельное осознанное включение `TELEGRAM_SEND_ENABLED=true`.

Формат payload, доступная аутентификация webhook, расчёт HMAC/timestamp и встроенный Telegram contact point проверены по [документации Grafana webhook contact point](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/webhook-notifier/), [Grafana Telegram contact point](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/integrations/configure-telegram/) и [общему описанию contact point](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/contact-points/) 2026-11-15.

## Приём текстовых файлов с согласием в личном чате

В личном чате `/file-help` объясняет цель и ограничения; перед обработкой пользователь должен отдельно отправить `/file-consent`. Команда `/file-stop` отзывает согласие. Согласие хранится в памяти и сбрасывается при перезапуске. Документы из групп игнорируются. Пример принимает только `.txt`, `.log`, `.java`, `.json` и `.csv`, если MIME-тип подходит к allowlist расширений и содержимое декодируется как UTF-8 текст без NUL-байтов. Имена с `/`, `\` или длиной больше 128 символов отклоняются; пользовательское имя никогда не используется в пути на диске. Пример считает строки и сообщает, найден ли простой шаблон stack trace. Содержимое не отображается, не исполняется, не распаковывается и не передаётся AI.

Значение `TELEGRAM_FILE_MAX_BYTES` по умолчанию — 1 MiB, и его нельзя увеличить выше текущего предела загрузки Bot API в облаке — 20 MB. Сначала проверяется размер из входящего Telegram document, затем размер из `getFile`, а поток загрузки повторно ограничивается при записи. Одновременно обрабатываются не более двух файлов. Используется документированный порядок Telegram: вызов `getFile`, затем загрузка по `https://api.telegram.org/file/bot<token>/<file_path>`; полученный путь считается недоверенным и проверяется. Файлы пишутся с правами только владельца во временную директорию `TELEGRAM_FILE_TEMP_DIR` (по умолчанию `${java.io.tmpdir}/telegram-private-uploads`) и удаляются в `finally` после успеха, отказа, ошибки загрузки или прерывания. Если файловая система не позволяет удалить файл, приложение выводит общее сообщение без имени пути и содержимого; оператору нужно очистить остаточные временные файлы. Пока идёт подсчёт, текст кратковременно находится в памяти процесса.

Загрузка отключена по умолчанию. Чтобы включить приём файлов в контролируемой среде, задайте `TELEGRAM_BOT_TOKEN`, установите `TELEGRAM_FILE_DOWNLOAD_ENABLED=true`, укажите приватную временную директорию с достаточным местом и настройте существующий секрет webhook. Это не включает отправку сообщений: `TELEGRAM_SEND_ENABLED` остаётся `false`, пока его не изменят отдельно. Пользователь должен сначала открыть бота в личном чате. В примере и тестах нет клиентских файлов, реальных Telegram ID, credentials или file ID. Тесты используют синтетический текст, подменный file gateway и локальный HTTP-сервер для проверки последовательности Bot API `getFile` → download.

Формат Bot API для файлов, текущие ограничения размера и срок действия ссылки проверены по [документации `getFile` и File](https://core.telegram.org/bots/api#getfile) 2026-11-15. Раскрытие цели, согласие на файл, отзыв и минимизация данных соответствуют [условиям разработчиков ботов](https://telegram.org/tos/bot-developers#4-privacy); production-продукту всё равно нужна доступная политика конфиденциальности и собственные применимые сроки хранения.

Проверка webhook синтетическим примером:

```bash
curl -i -X POST http://localhost:8080/telegram/webhook \
  -H 'Content-Type: application/json' \
  -H 'X-Telegram-Bot-Api-Secret-Token: local-demo-secret' \
  -d '{"message":{"message_id":1,"chat":{"id":12345,"type":"private"},"from":{"id":12345},"text":"/start"}}'
```

Профиль `demo` задаёт открытый локальный placeholder для заголовка webhook. Сервер пишет только отметку dry-run, не раскрывая ни текст, ни получателя, и возвращает HTTP 200. Попробуйте `/ai-help`, `/consent`, `/ask Пример запроса`, затем `/ai-confirm`. Точный текст вопроса хранится только в оперативной памяти процесса (не сохраняется на диск) до подтверждения, отмены, отзыва согласия или перезапуска; до `/ai-confirm` вызова провайдера нет. Команда `/ai-cancel` удаляет ожидающий запрос, а `/stop` отзывает согласие и очищает его. В запрос не добавляются история чата, файлы, сообщения Business или других пользователей. Без настроенных учётных данных Anthropic подтверждение также не вызовет сеть. Без секрета webhook (или явного профиля `demo`) endpoint вернёт HTTP 503.

Откройте `http://localhost:8080/`, чтобы посмотреть форму Mini App. Обычный браузер не передаёт подписанные Telegram данные `initData`, поэтому endpoint отправки и проверки статуса отклонит запрос без свежего launch payload и `TELEGRAM_BOT_TOKEN`. Учётных данных здесь нет, поэтому аутентифицированную отправку заявки в локальном демо выполнить нельзя. Форма передаёт сырые `initData` в теле HTTPS POST-запроса и не считает `initDataUnsafe` или присланный браузером Telegram ID доказательством личности.

Backend предоставляет `POST /api/miniapp/requests` для проверки launch data и создания заявки, а затем `POST /api/miniapp/requests/status` для получения статуса. Владелец определяется по подписанному полю `user`; прикладное правило разрешает проверенному пользователю создать собственную заявку и читать только её. Другой пользователь с корректной подписью получит 404. В процессе хранится не более 1 000 записей, они исчезнут после перезапуска и не разделяются между экземплярами. До публикации замените хранилище долговременным и повторно проверяйте права при каждой операции с записью. Пример не публикует результат в Telegram и не требует права отправлять сообщения в чат. Если Mini App открыли из группы, `chat_instance` считается только контекстом: пример не использует его для доступа и не получает историю группы. Публикуйте Mini App только по HTTPS и задайте URL запуска в настройках контролируемого бота; здесь нет публичного URL и настроенного бота.

### Общая доска Mini App для группы

На той же странице есть синтетическая доска доступности для нескольких участников. `POST /api/miniapp/shared/board` возвращает состояние и слоты текущего подписанного пользователя; `POST /api/miniapp/shared/availability` заменяет его вклад с версией доски, полученной при чтении. Общий ответ содержит только количество желающих на каждый слот, без Telegram ID и индивидуальных вариантов других участников. Повтор идентичного запроса ничего не меняет; устаревшее конкурирующее изменение возвращает HTTP 409 и актуальную доску.

Backend принимает только свежую подписанную `initData` с полями `user`, `chat_instance` и `chat_type` со значением `group` или `supergroup`. Затем он проверяет точную пару из `TELEGRAM_MINIAPP_SHARED_ALLOWED_MEMBERSHIPS` в формате списка `chat_instance=user_id` через запятую. Пустое значение запрещает весь доступ. Значения чата и пользователя из браузера не используются. `chat_instance` задаёт контекст, но не подтверждает членство в группе; права задаёт allowlist приложения. Mini App не получает историю группы и не может писать от имени пользователя.

Состояние хранится только в памяти процесса: максимум 500 досок, 50 участников на доску и 8 слотов на вклад. При рестарте состояние теряется и между экземплярами не разделяется. Синхронизированный in-memory compare-and-set показывает защиту от потерянных обновлений внутри одного процесса; production-варианту нужны общее постоянное хранилище и транзакционное/атомарное условное обновление. Allowlist — учебная граница авторизации, а не справочник участников production-группы. Тесты используют синтетические данные и не подключаются к Telegram. См. [J18](../../tasks/completed-issues/J18.md) и [урок об общей Mini App](../../learning/04-mini-apps.md).

## Telegram Business: поддержка и передача оператору

`/telegram/webhook` принимает типы обновлений `business_connection`, `business_message`, `edited_business_message` и `deleted_business_messages` после обычной проверки webhook-секрета и `update_id`. При регистрации настоящего webhook добавьте эти типы в `allowed_updates`. Владелец бизнес-аккаунта должен явно подключить Business-enabled бота и выбрать личные чаты и права в Telegram. Выбор получателей контролирует Telegram; пример не трактует подключение как доступ к группам или ко всему архиву аккаунта. Адаптер использует только `can_reply`; ему не нужны права чтения и удаления сообщений, редактирования профиля или другие права Business.

Адаптер создаёт тестовую ссылку на заявку, ссылку на диалог/сообщение, статус, назначение в очередь или оператору, а также идентификаторы изменений и удалений. Текст сообщений намеренно не сохраняется, transcript не копируется. Повторная доставка Business-обновлений защищена существующим реестром update ID. Обновление подключения содержит `is_enabled` и права; `can_reply` относится к личным чатам, где входящее сообщение получено за последние 24 часа. Метод ответа оператора проверяет его по allowlist, назначение заявки, активность подключения, `can_reply` и время последнего входящего сообщения и лишь затем вызывает `sendMessage` с `business_connection_id` и `chat_id`. При отказе любой проверки он выдаёт инструкцию ответить вручную и не вызывает Telegram.

Для тестовой авторизации задайте `TELEGRAM_BUSINESS_OPERATOR_IDS` как список ID через запятую. В примере нет интерфейса оператора, helpdesk-очереди, постоянного хранилища заявок и настоящего Business-аккаунта; тесты напрямую вызывают service с mock sender. Реальный интерфейс должен отдельно аутентифицировать сотрудников, проверять назначение при действии и использовать постоянное хранилище, идемпотентность и правила удаления данных. ID Telegram сами по себе не подтверждают роль сотрудника.

Business-данные не отправляются в AI или сторонние системы. Условия Bot Developer требуют раскрывать цель и сроки хранения и запрещают передавать Business-сообщения и файлы третьим лицам без разрешения пользователя. Аккаунт Business, диалог клиента, helpdesk и реальные сообщения не использовались. Модель Business-обновлений Bot API, права подключения и `sendMessage.business_connection_id` проверены по [Bot API Telegram](https://core.telegram.org/bots/api#businessconnection), [описанию подключённых Business-ботов](https://core.telegram.org/api/bots/connected-business-bots) и [условиям Bot Developer](https://telegram.org/tos/bot-developers) 15 ноября 2026 года.

## Сбор заявки на продажу с явным согласием и HubSpot

Сценарий личного чата: `/sales` → `/sales-consent` → `/sales-submit email|имя|фамилия|компания`. Команда `/sales` заранее раскрывает точные поля и получателей, `/sales-stop` отзывает согласие в памяти процесса. Пользователь сам вводит поля; Telegram ID, username, профиль, участие в группах и история чата не копируются. Согласие отправить заявку на продажу не является согласием на маркетинговую рассылку.

Адаптер Java использует актуальную версию HubSpot API `2026-09` с batch upsert по email. Записываются только `email`, `firstname`, `lastname`, `company` при наличии и настроенный `hubspot_owner_id`; без ID владельца запись заблокирована. Клиент получает CRM reference. Менеджер получает название очереди и reference, но не контактные поля. Повторная заявка с тем же email использует тот же ключ контакта; подавление повторного уведомления работает только в памяти текущего процесса. Пример не создаёт сделку, не подписывает контакт на маркетинг и не проверяет, существует ли owner ID в целевом HubSpot.

Для настройки в контролируемой среде HubSpot private app/OAuth grant должен содержать `crm.objects.contacts.write`; в портале должен существовать владелец и быть разрешена запись полей. Начиная с версии API `2026-09`, HubSpot применяет в API настроенные в портале требования к созданию записи: администратор может сделать обязательными дополнительные свойства и отклонить payload примера. До живой записи проверьте настройки портала. Версия API, batch upsert и правила валидации проверены по [обзору HubSpot API](https://developers.hubspot.com/docs/api-reference/latest/overview), [batch upsert контакта](https://developers.hubspot.com/docs/api-reference/latest/crm/objects/contacts/batch/upsert-contacts) и [объявлению о валидации версии 2026-09](https://developers.hubspot.com/changelog/crm-api-write-validation-enforcement) 15 ноября 2026 года.

```bash
HUBSPOT_ACCESS_TOKEN='<токен HubSpot private app или OAuth>' \
HUBSPOT_OWNER_ID='<ID владельца из целевого портала>' \
TELEGRAM_SALES_MANAGER_CHAT_ID='<разрешённый ID чата менеджеров>' \
SALES_QUEUE_NAME='Демо-очередь продаж' \
TELEGRAM_SEND_ENABLED=false \
./gradlew bootRun
```

Тесты используют fake CRM gateway, mock HTTP transport и синтетические webhook updates. HubSpot, Telegram, клиентские данные и живые записи/сообщения не использовались. Согласие и дедупликация обновлений/уведомлений хранятся в памяти и теряются после перезапуска. Для production нужны постоянная запись согласия и аудита, ключ идемпотентности и outbox, правила хранения/удаления данных, политика обновления существующих CRM-контактов и отдельная авторизация интерфейса менеджера. Это пример сбора контакта, не полная CRM/helpdesk интеграция.

## Приватная заявка сотрудника и подтверждение менеджера

Бот не может первым начать личный чат. Сотрудник должен открыть его и отправить `/internal-help`. `/request IT|краткое описание` принимает одну из тестовых категорий и ограниченное по длине описание. Приложение отправляет номер заявки, категорию и переданное описание в настроенный `TELEGRAM_INTERNAL_APPROVAL_CHAT_ID`, добавляя кнопки выбора approve/reject. Выбор ещё не меняет статус: тот же менеджер должен подтвердить его отдельным callback в течение десяти минут. `/request-status <номер>` показывает статус только заявителю или настроенному менеджеру.

`ConfiguredInternalRoleDirectory` сопоставляет указанные на сервере Telegram ID с ролями employee/manager из `TELEGRAM_INTERNAL_EMPLOYEE_IDS` и `TELEGRAM_INTERNAL_MANAGER_IDS`. Приложение проверяет роль при создании заявки, получении статуса, выборе действия и подтверждении; права администратора Telegram и поля update не выдают корпоративные роли. Это только демонстрационный allowlist. В production свяжите Telegram аккаунт с отдельно проверенной учетной записью сотрудника (например, SSO) и используйте корпоративную identity/authorization систему как источник прав.

Статус заявки, её владелец, ожидающий токен подтверждения и минимальный аудит (actor, действие, UTC timestamp, результат) хранятся только в ограниченной памяти процесса. Описание удаляется из памяти после отправки в чат согласования. Повтор той же update в процессе использует прежний номер заявки; если Telegram принял уведомление, но ответ потерялся, при retry возможно повторное уведомление. История переписки не копируется; HR/ITSM не подключены. При перезапуске статус и аудит исчезают; реестр callback updates тоже локальный. Для production нужны постоянное защищённое хранилище заявок и аудита, правила хранения/удаления, общий idempotency store и outbox, а также аутентифицированный интерфейс менеджера. AI не требуется.

Локальная конфигурация использует только синтетические идентификаторы; реальные отправки отключены:

```bash
TELEGRAM_INTERNAL_EMPLOYEE_IDS='10001,10002' \
TELEGRAM_INTERNAL_MANAGER_IDS='20001' \
TELEGRAM_INTERNAL_APPROVAL_CHAT_ID='-1001234567890' \
TELEGRAM_SEND_ENABLED=false \
./gradlew bootRun
```

Тесты используют fake identity directory и синтетические webhook/callback updates. Проверяются неизвестный сотрудник, статус только для владельца, неверный менеджер/чат, отдельное подтверждение, approve/reject, истечение подтверждения, устаревший callback, безопасный повтор подачи и минимизация аудита. Внутренняя группа, аккаунт сотрудника или сообщение не использовались. Запрет боту инициировать приватный чат и ограничения callback проверены по [описанию Telegram-ботов](https://core.telegram.org/bots) и [Bot API](https://core.telegram.org/bots/api#inlinekeyboardbutton) 15 ноября 2026 года.

## Секреты для отдельной контролируемой среды

Секреты передаются через переменные окружения. `TELEGRAM_SEND_ENABLED=false` задан по умолчанию. Оставляйте его выключенным. Включение разрешит реальный вызов Bot API при получении обновления; для локального изучения это не нужно.

Последовательность команд: `/ai-help` → `/consent` → `/ask <вопрос>` → прочитать запрос подтверждения → `/ai-confirm`. Для каждого вопроса требуется отдельное явное подтверждение. `/ai-cancel` удаляет подготовленный запрос; `/stop` отзывает согласие и удаляет ожидающий текст. Только `/ai-confirm` может вызвать настроенный Anthropic Messages API; в запрос передаётся ровно текст вопроса пользователя. История, файлы, сообщения группы, содержимое других пользователей и сообщения Telegram Business не собираются. Текст ожидающего запроса хранится только в оперативной памяти процесса и не сохраняется на диск; приложение не сохраняет вопросы или ответы. Anthropic указывает, что API-входы и ответы обычно удаляются из backend в течение 30 дней, с исключениями для закона, контроля соблюдения правил или отдельного соглашения; см. [условия хранения](https://privacy.anthropic.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data). Текущие условия раскрываются пользователю, но перед реальным использованием проверьте тариф и актуальные условия провайдера. `/human` отмечает запрос на связь с человеком в памяти, но оператор/helpdesk в демо не подключён. Это пример ограниченного сценария, а не заключение о соответствии Telegram для любого внедрения.

```bash
TELEGRAM_BOT_TOKEN='<секрет тестового бота>' \
TELEGRAM_WEBHOOK_SECRET='<случайный секрет webhook>' \
TELEGRAM_SEND_ENABLED=false \
ANTHROPIC_API_KEY='<ключ провайдера>' \
ANTHROPIC_MODEL='<доступная модели вашему аккаунту>' \
./gradlew bootRun
```

Не коммитьте настоящие значения, `.env`, Telegram launch payload, ID пользователей или журналы с текстом сообщений. Файлы сессий TDLib и каталог `telegram-data/` игнорируются Git. Проверка репозитория ищет распространённые форматы Bot API, Anthropic, OpenAI и Telegram API hash, но не является полным детектором секретов. Ограниченный in-memory реестр хранит не более 10 000 ID, устраняет дубликаты только в одном процессе и очищается при перезапуске; он не гарантирует ровно одну внешнюю отправку, если провайдер принял запрос, но ответ потерялся. Для production нужны долговременная общая идемпотентность и outbox внешних эффектов. Для публичного webhook нужны HTTPS, секрет webhook Telegram, ограничение размера запроса, лимиты запросов и сохранение согласий; ключи следует хранить в менеджере секретов.

## Проверка Mini App

Передайте `Telegram.WebApp.initData` на backend бота. Для проверки по Bot API сначала вычислите `secret_key = HMAC_SHA256(key="WebAppData", message=bot_token)`, затем `hash = HMAC_SHA256(key=secret_key, message=data_check_string)`. Сравните итоговый hex hash за постоянное время и отклоняйте устаревший `auth_date`; в этом примере срок — 15 минут. Проверенный Telegram ID подтверждает личность в Telegram, но не заменяет авторизацию приложения: для доступа к данным CRM и выполнения действий нужны собственные проверки аккаунта и ролей. См. [официальную процедуру проверки Mini App](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## Ограничения

- Bot API получает только обновления, доступные боту. Команда `/ask` намеренно запрещена в группах.
- Пример голосования обрабатывает только явную команду и callback-запросы; он не получает список участников и не выводит роли из разрешений Telegram-группы.
- Внутренний процесс доверяет только server-side demo справочнику ролей, а не ролям группы Telegram; заявка и аудит хранятся временно, согласование не заменяет SSO или ITSM.
- Уведомления Jira требуют, чтобы администратор зарегистрировал HTTPS webhook с совпадающим секретом и нужными событиями; локальные тесты не проверяют реальный Jira tenant или доставку.
- Подтверждения Grafana существуют только в приложении; пример не меняет состояние alert в Grafana и не вызывает Grafana API.
- Приём файлов доступен только в личном чате после согласия; файлы удаляются после обработки и загрузка выключена по умолчанию.
- Mini App может получить ограниченный контекст запуска из группы, но этот пример не использует его для авторизации и не получает историю группы или право писать от имени пользователя.
- AI выключен без учётных данных провайдера. Согласие, ожидающий запрос и отметка передачи человеку хранятся только в памяти демо; для каждого вопроса требуется отдельная команда `/ai-confirm`. `/human` лишь ставит отметку, так как очередь операторов не подключена.
- Этот проект не подключался к реальному боту или провайдеру; живая интеграция не проверялась.
- `./gradlew test` проверяет только локальное поведение; подписи Mini App синтетические. Тесты не подтверждают запуск внутри Telegram, доставку, доступность провайдера или авторизацию аккаунта.

## Смоделированный цикл оплаты Telegram Stars

Команда `/buy-demo` в личном чате создаёт локальный reference `STARS-...`; `/paysupport` показывает границы учебного сценария. Приложение не вызывает `sendInvoice`, поэтому настоящий клиент Telegram не может оплатить этот заказ. Тесты сервиса подают синтетические `pre_checkout_query` и `successful_payment` через fake-адаптер. Проверяются владелец заказа, валюта `XTR`, точная сумма и срок действия; синтетическое право выдаётся только после успешного платежа. Повторные update и charge ID не приводят к повторной выдаче. `/refund-demo <order-reference>` проверяет владельца и вызывает только fake-адаптер возврата.

Сфокусированные тесты: `./gradlew test --tests example.telegram.TelegramStarsPaymentServiceTest --tests example.telegram.TelegramWebhookControllerTest`. Заказ и идемпотентность хранятся только в памяти процесса, очищаются при перезапуске и не разделяются между экземплярами. Проверка десятисекундного окна основана на локальных часах и не измеряет сетевой обмен с Telegram. Это учебный пример, а не production-платёжная интеграция. См. [J19](../../tasks/completed-issues/J19.md) и [урок о Stars](../../learning/09-stars-payments.md).

## Telegram Login OIDC для сайта

Откройте `/telegram-login-demo.html`, чтобы посмотреть обычный сайт с кнопкой входа. Функция по умолчанию выключена; включать её можно только в отдельно разрешённой конфигурации с `TELEGRAM_LOGIN_OIDC_CLIENT_ID` и `TELEGRAM_LOGIN_OIDC_CLIENT_SECRET` на сервере. По умолчанию используется issuer `https://oauth.telegram.org` и запрашивается только `openid`. Redirect URI по умолчанию — `{baseUrl}/login/oauth2/code/telegram`; задайте `TELEGRAM_LOGIN_OIDC_REDIRECT_URI`, если публичный origin нельзя надёжно определить. Перед живым входом в @BotFather нужно зарегистрировать origin сайта и точный callback URI. Scopes `profile`, `phone` и `telegram:bot_access` добавляйте только при понятной необходимости и после явного разрешения пользователя.

Spring Security обрабатывает OIDC-запрос, связывание `state` и `nonce`, PKCE S256, повторное использование redirect URI, проверку подписи по JWKS, issuer, audience и срока действия токена. У Telegram Login нет отдельного UserInfo endpoint; тест с fake issuer проверяет использование подтверждённого ID token без него. `/login-demo/me` возвращает только `sub` вошедшего пользователя: Telegram subject подтверждает identity, но не является ролью или разрешением в приложении. Этот вход использует серверную HTTP-сессию; реальному сайту с несколькими экземплярами потребуется общее хранилище сессий или подходящая affinity-настройка и отдельная проверка безопасности. Существующие webhook и Mini App сохраняют собственные способы проверки.

Локальные синтетические callback-тесты: `./gradlew test --tests example.telegram.TelegramLoginOidcSecurityTest`. Они запускают issuer только на loopback и используют синтетические RSA-ключи, claims, credentials клиента и callback; внешние запросы к Telegram или identity provider не выполняются. См. [J20](../../tasks/completed-issues/J20.md) и [урок по входу на сайт](../../learning/10-telegram-login-oidc.md).

Необязательная офлайн-лаборатория J24 — отдельный шов: `POST /chatwoot/webhook` проверяет HMAC Chatwoot по timestamp и исходным байтам тела до маршрутизации ссылок на входящие текстовые сообщения. Telegram webhook и канал по-прежнему принадлежат Chatwoot. Команда `./gradlew demoChatwootSupport` в этом каталоге запускает синтетический сценарий без сети. Ранний фильтр ограничивает тело до его материализации Spring. Повтор определяется по account/message ID в подписанном теле; `X-Chatwoot-Delivery` не подписан и не используется как доверенный ключ идемпотентности. Текст временно разбирается, но не сохраняется швом передачи или fake. Реестр и состояние handoff ограничены и локальны для процесса; они не переживают перезапуск и не синхронизируются между экземплярами. См. [J24](../../tasks/completed-issues/J24.md) и [урок](../../learning/08-chatwoot-support.md).

### Офлайн-пример маршрутизации Jira `Blocks`

`./gradlew demoJiraBlocksRouting` запускает локальный синтетический разбор узкой гипотезы маршрутизации из CVN-1156. Notice создаётся только для новой активной явной межкомандной связи; получателем становится команда заблокированной задачи. Входные события группируются по target, повтор relation/state подавляется, а same-team, unknown/dual-team, неоднозначные epic, исторические связи и задачи, завершённые до запуска demo, игнорируются. Снятие, удаление, завершение или повторное открытие связи записывается только для relation, по которой fake уже сохранил notice. Fake хранит лишь синтетические ссылки и счётчики; demo выводит названия сценариев и итоговые числа, но не тексты уведомлений.

Focused-тесты policy: `./gradlew test --tests example.telegram.JiraBlocksRoutingPolicyTest`. Это одноразовый пример с состоянием только в памяти процесса, а не интеграция с Jira или Telegram. Сетевых вызовов и credentials нет, исторические связи не загружаются. Реальная маршрутизация и эффект Telegram остаются неизвестными; сообщённая потребность основана на словах одного внутреннего участника и этим примером не измеряется.
