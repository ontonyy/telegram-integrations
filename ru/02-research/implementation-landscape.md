# Реальные реализации Telegram: приложения, мосты и коннекторы данных

**Проверено:** 14 ноября 2026 года. Изучены метаданные GitHub, документация проектов и отдельные исходные файлы. Сторонние проекты не устанавливались и не запускались. Ветки GitHub меняются — перед выбором проверьте исходники по ссылкам.

## Как читать каталог

- **Приложение** — сервис с собственным процессом и инструкциями по эксплуатации.
- **Мост** — слой управления/передачи сообщений от Telegram к уже установленной программе или агенту. Он не заменяет модель и сам coding agent.
- **Библиотека** — код для встраивания в приложение, а не готовый продукт для пользователей.
- **Прототип / ранний проект** — у репозитория есть код и документация, но проект недавно создан, имеет мало признаков зрелого выпуска, ограниченную аудиторию или узкую проверенную область. Это не аудит безопасности.
- Функции ниже **заявлены проектом и подтверждены его документацией/исходниками**, но не проверялись нами в production. «Не запускался» означает, что мы не устанавливали, не настраивали и не запускали проект.

У self-hosted мостов часто нет платы за лицензию согласно лицензии репозитория, но остаются расходы на хостинг, ОС, подписку/API модели, speech-to-text и сопровождение. За обычные сообщения Bot API Telegram отдельной платы не берёт. Не используйте реальные учётные данные, пока не проверите точный commit, разрешения, обновление, зависимости и обращение с данными.

### Рецепт безопасного пилота управления с телефона

1. Создайте отдельного Telegram-бота и используйте один личный чат владельца; настройте явный список числовых user ID.
2. Запускайте мост от отдельного пользователя ОС с доступом только к одноразовому clone или выбранному non-production репозиторию. Не храните рядом production-секреты, выгрузки клиентов и пользовательские Telegram-сессии.
3. Оставьте включёнными штатный sandbox и подтверждения агента. Начните с просмотра статуса, review и тестов, затем разрешите небольшое обратимое изменение в тестовой ветке. Не начинайте с bypass-флагов.
4. Не отправляйте логи и вывод проекта в общие группы. Если позже потребуется группа, каждый участник должен быть доверенным и иметь отдельное разрешение на управление агентом; упоминание бота — только маршрутизация, не контроль безопасности.
5. Ограничьте набор действий: проверить состояние, запустить выбранный check, подготовить patch. Деплой, merge, секреты, миграции, внешние сообщения и production-доступ оставьте вне Telegram-моста.

Это предлагаемая схема контроля. Allowlist Telegram и подтверждения проекта не заменяют sandbox ОС, code review и подтверждение самого агента.

### Правила по данным и технические ограничения

Условия Telegram по [лицензированию контента](https://telegram.org/tos/content-licensing) запрещают scraping, индексацию, сбор, агрегацию и использование данных платформы для AI/ML, включая разработку, улучшение, бенчмаркинг и deployment. Указанное исключение требует явного, информированного, утвердительного и продолжающегося согласия **каждого затронутого пользователя**, ограниченного конкретным содержимым и чатом/контекстом; согласие в одном контексте не даёт прав на другой. [Условия для разработчиков ботов](https://telegram.org/tos/bot-developers) отдельно запрещают собирать данные сверх необходимого для сервиса и сбор для создания больших наборов, моделей или AI-продуктов. Они допускают обработку содержимого, которое пользователь напрямую и добровольно отправил боту, если ясно раскрыта цель и каждый пользователь дал индивидуальное, явное, активное и отзывное согласие. Для Business-данных запрещено передавать содержимое/файлы сторонним API без авторизации пользователя.

Путь прямого сообщения боту не разрешает автоматически суммаризировать группы, индексировать историю, обучать модель или отправлять переписки Business в Claude/OpenAI. Для содержимого группы сначала нужно определить всех затронутых участников и согласие каждого в рамках соответствующего чата/контекста; до проверки условий и юриста такую функцию не создавать. Если применимость правил неясна, исключите содержимое Telegram и используйте отдельный запрос пользователя или одобренную базу знаний.

Технический доступ зависит от механизма:

- **Bot API** предоставляет доступные конкретному боту входящие updates, а не произвольный поиск по истории. Privacy mode в группе ограничивает обычного бота сообщениями/командами, адресованными ему; администратор или бот с выключенным privacy mode получает больше текущих сообщений, но это не произвольный API старой истории.
- **Telegram Business** позволяет выбрать **личные чаты**: существующие/новые, контакты/не контакты или отдельных пользователей с исключениями. Права отдельно контролируют чтение, ответ и действия с аккаунтом. Подключённый бот получает business-message updates для выбранных чатов, но не все группы или полный архив аккаунта. По текущим Business rights отвечать можно в личных чатах только при входящем сообщении за последние 24 часа.
- **TDLib/MTProto** работает как клиент Telegram, авторизованный пользователем, и может получать данные из чатов, видимых аккаунту. Это расширяет технический доступ, но не согласие и не разрешения по лицензии.
- **MCP** описывает интерфейс инструментов. Фактическую область задают код сервера, учётные данные, конфигурация и подтверждения клиента. Аннотация/надпись «read-only» не является разрешением Telegram.

До подключения попросите поставщика показать на тестовом бизнес-аккаунте типы входящих событий, имя отправителя, хранение файлов, атрибуцию оператора, назначение и передачу диалога человеку. Не подключайте production Business inbox для оценки.

## Практические схемы

### 1. Создание обращения и передача оператору

`клиент пишет боту → Bot API → сервис обращений/helpdesk → очередь/назначение → ответ оператора от имени бота`

Клиент видит короткое меню, номер обращения и ответ. Helpdesk показывает диалог, файлы, присланные клиентом, и историю тикета. Бот получает только переписку с собой. Команда `/human` или кнопка «связаться с поддержкой» переводит обращение в очередь оператора. Сначала достаточно обычных правил — AI не нужен. Если модель готовит ответ, отправляйте только выбранное клиентом содержимое и одобренную базу знаний после раскрытия цели и отзывного согласия; менеджер проверяет и отправляет черновик вручную.

### 2. Совместное решение в группе

`тема группы → Telegram poll или явные кнопки → backend сохраняет выбор → результат публикуется в этой теме`

Для выбора времени встречи проще всего нативный Telegram poll; AI не нужен. Для общего заказа или таблицы доступности подойдет Mini App по direct link с backend-состоянием, связанным с проверенным пользователем и контекстом чата. В direct-link режиме Mini App получает `chat_type` и `chat_instance`, но не читает сообщения и не публикует от имени пользователя. Участники работают в web app, а публикация результата в чат требует отдельного явного действия пользователя.

### 3. Панель менеджера на телефоне

`уполномоченный сотрудник → direct link Mini App → сервер проверяет initData → backend проверяет компанию/роль → список/действие → событие аудита`

Telegram здесь только запускает интерфейс. Backend остаётся источником полномочий; Telegram ID из `initData` не равен роли в CVNoor/CRM. Это полезно, если собственная мобильная web-страница неудобна. Для простого уведомления или кнопки «подтвердить получение» достаточно Bot API callback и backend-проверки.

### 4. Сессия разработки с телефона

`личный allowlisted Telegram чат → self-hosted bridge → sandboxed Codex/Claude CLI → выбранная копия репозитория`

Начните с проверки статуса, review и тестов в изолированной копии. Оставьте подтверждения агента включёнными. Не подключайте группу, если все участники не могут управлять агентом в этом репозитории и на этом хосте. Не отправляйте в Telegram логи с секретами и пользовательскими данными. Смотрите таблицу проектов; ни один сторонний мост здесь не запускался.

### 5. AI по явно присланному содержимому, а не по архиву чатов

`пользователь сам отправляет вопрос/файл боту → раскрытие цели и согласие → проверка типа/размера файла → выбранный текст модели → ответ или черновик человеку`

Используйте личный диалог с ботом для вопросов по одобренной базе знаний. Если анализируется файл, который пользователь отправил сам, объясните, какая модель получит его извлечённое содержимое, ограничьте хранение и дайте возможность удаления/отказа. Не создавайте индекс TDLib/MCP по истории, пока не выполнены условия узкого согласия всех релевантных участников и проверка юристом именно для этих данных и контекста.

## Граница Java/Spring Boot

Для обычных уведомлений и команд Spring Boot принимает Bot API webhook, проверяет Telegram secret header, валидирует update и вызывает небольшой adapter. [TelegramBots](https://github.com/rubenlagus/TelegramBots) и [Pengrad Java Telegram Bot API](https://github.com/pengrad/java-telegram-bot-api) — библиотеки, а не helpdesk и не AI-агенты; для исходящего `sendMessage` достаточно Java `HttpClient` по HTTPS. Используйте очередь/outbox только если нужна надёжная повторная доставка; заранее определите идемпотентность, лимиты и удаление данных.

Для существующего Java backend предпочтительны следующие границы:

- исходящее событие: domain event → политика получателя/согласия → outbox или ограниченная очередь → Bot API adapter → результат доставки;
- входящее действие: update → проверка webhook secret → разрешённая команда → актуальная доменная авторизация → запись аудита;
- Mini App: launch data → проверка HMAC и срока действия на сервере → авторизация приложения → бизнес-действие;
- Business: библиотека и бот должны поддерживать Business и передавать `business_connection_id`; обычный `sendMessage` не начинает автоматически отправлять от аккаунта Business;
- TDLib: изолируйте JNI-клиент и пользовательскую сессию от stateless API, если продукт не является полноценным Telegram-клиентом.

В существующем [примере Java/Spring](../../examples/java-spring/README.md) нет реального токена и по умолчанию используется локальный dry run. Статус запуска описан в README примера; в этом исследовании пример не запускался.
