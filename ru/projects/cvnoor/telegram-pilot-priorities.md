# Приоритеты пилотов Telegram для CVNoor

**Статус:** исследование и предложенный порядок, не утверждённое поведение продукта. **Проверено:** 14 ноября 2026 года. Backend checkout CVNoor проверен только для чтения: локальная `main` совпала с `origin/main` на commit `4badd4d0`; в checkout были посторонние незатреканные файлы, репозиторий не изменялся. Сообщения Telegram не отправлялись, секреты не просматривались, live-окружение не подключалось.

## Текущее состояние интеграций

В backend и workflows CVNoor уже есть несколько сценариев Telegram. В проверенном исходном коде:

- `telegram-release.yml` публикует одно best-effort сообщение Bot API о стабильном релизе в настроенную тему группового чата. При повторном запуске или неопределённом timeout возможен дубль.
- Обработка ошибок workflow отправляет название workflow/job, короткий SHA коммита и ссылку на GitHub Actions run; логи ошибок не отправляются. Недоступность Telegram не меняет результат workflow.
- `TelegramAlertSender` отправляет внутренние уведомления о 500, повторяющихся 503, аномалиях и пороговых счётчиках неудачных входов в один настроенный чат/тему. Отправка асинхронная; очередь в памяти ограничена, дедупликация/лимиты в памяти процесса. При переполнении или ошибке провайдера сообщения могут теряться. Это не durable outbox.
- В общем репозитории Telegram теперь есть [J16 — учебный outbox на H2](../../../tasks/completed-issues/J16.md). Он показывает постоянную постановку, lease, ограниченные повторы, истечение срока и Telegram `retry_after`; он не подключён к CVNoor и не проверяет PostgreSQL outbox CVNoor, контракт sender или живую доставку.
- Workflow деплоя передаёт параметры Telegram для non-production Cloud Run и включает флаг алертов. Документация API отмечает версию токена в Secret Manager и grant сервисному аккаунту как `UNKNOWN`. Матрица проверок не доказывает получение реального Telegram-сообщения. Наличие настройки и mocked tests не доказывают live-доставку.

Это внутренние операционные/release-сценарии на обычном Bot API. В проверенных исходниках API не найдено подтверждения пользовательской привязки аккаунта Telegram, предпочтений кандидата/работодателя, helpdesk, подключения Telegram Business, Mini App, входящего customer-бота или TDLib-клиента. Перед выводом об отсутствии проверьте актуальные ветки и work items.

Существующий backend scope включает CVN-521 (алерты API), CVN-529 (алерты аномалий) и CVN-550 (алерты workflow/зависимостей). До создания новых задач проверьте актуальный статус этих тикетов. Заметки API в этом репозитории отделяют уже существующие алерты от будущих пользовательских сообщений.

## Метод приоритизации

Оценки качественные и отражают ожидаемую пользу, чувствительность доступа, объём реализации и удобство телефона. Это исследовательская оценка, а не измеренный спрос или решение владельца. «Техническая зрелость» оценивает механизм Telegram/готовый продукт; «состояние CVNoor» — что подтверждается просмотренным исходным кодом.

### Почему такой порядок

1. Внутренние алерты решают понятную задачу команды, но сначала нужно подтвердить фактическую доставку и учитывать, что in-memory sender может терять сообщения.
2. Уведомление работодателю может улучшить рабочий процесс, сохраняя детали за существующей авторизацией сайта.
3. Уведомления кандидату могут ускорить получение статуса и напоминаний, но возраст пользователей, opt-in и конкуренция с email/in-product сообщениями делают сценарий более чувствительным.
4. Готовый helpdesk может быстрее дать реальную очередь операторов, чем собственная панель; до выбора проверьте, кто именно отправитель и поддерживается ли нужный Business режим.
5. Mini App или согласование Telegram оправданы только если есть подтверждённая проблема с мобильным UX. Telegram-контекст не разрешает доменное действие.
6. AI лучше сначала использовать как помощника оператора для одного выбранного обращения и утверждённой базы знаний. Для алертов, маршрутизации, напоминаний и порогов AI не нужен.
7. Удалённое кодирование — эксперимент для рабочей среды разработчика, не функция для клиентов CVNoor и не runtime production.

В просмотренных материалах нет оснований считать, что CVNoor нужен бот для чтения истории группы или общая Mini App. Для решения о времени вебинара может подойти обычный Telegram poll; не храните данные кандидатов/заявок в группе.

## Предлагаемый порядок будущих тикетов

1. **Сверить текущие алерты.** Проверить CVN-521/CVN-529/CVN-550, provisioning runtime-секрета и владельца адресата через уполномоченного владельца; получить безопасное подтверждение доставки в non-production. В рамках исследования сообщение не отправлялось.
2. **Принять решение о клиентских уведомлениях.** Определить роли, цели, каналы, opt-in/отвязку, локаль, возраст/safeguarding, минимальный текст и подавление. Сравнить с email/in-product.
3. **Описать пилот для работодателя.** Привязка участника компании, backend-авторизация, нейтральный текст, защищённая ссылка, идемпотентность, срок действия и поведение при сбое. Использовать синтетическую компанию/пользователя non-production.
4. **Оценить helpdesk.** На тестовом аккаунте показать обычный Bot API inbox и поддерживаемый Business режим (если компании важно отвечать от профиля), включая передачу человеку.
5. **Уведомления кандидатам.** Только после решения шага 2; сначала одно событие и один язык, затем настройки языка, отказа и напоминаний.
6. **Mini App и AI.** Создавать после подтверждения необходимости для телефона. Не использовать содержимое Telegram с AI до одобрения конкретного согласия, правовых условий и провайдера.

Это будущие заготовки, а не тикеты, одобренные планы, разрешение создавать credentials или отправлять сообщения. На этапе реализации перечитайте актуальные планы и код CVNoor API.
