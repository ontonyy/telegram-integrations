# Возможности Telegram для CVNoor API

**Статус:** проектные заметки, не план реализации. **Read-only проверка API checkout:** локальная `main` совпала с `origin/main` на `4badd4d0` 14 ноября 2026 года. В этом исходнике уже есть исходящие operational alerts Bot API и уведомления workflow/release. Этот репозиторий не добавляет код или credentials в API; сообщений не отправляли.

## Контекст backend

Backend: Java 25, Spring Boot 4.1.1, Gradle multi-module. Clerk — источник идентичности; Supabase PostgreSQL — текущий MVP-провайдер данных; API отвечает за авторизацию доменных операций. Документация backend описывает PostgreSQL transactional outbox как принятый механизм фоновой работы, но перед реализацией нужно перепроверить его текущий статус проверки и включение в целевом checkout. Outbox — механизм доставки, а не согласие на уведомления и не доказательство успешной доставки Telegram.

Канонические документы репозитория CVNoor API:

Telegram-интеграция должна сохранить stateless-границу API, использовать текущую модель идентичности/прав, не хранить секреты провайдера в исходном коде и соответствовать структуре модулей/пакетов. Перед кодом или тикетами заново прочитать целевую ветку и активные планы.

## Предлагаемая граница интеграции

Использовать Telegram как провайдер исходящих уведомлений и дополнительный канал действий. Доменная логика создаёт типизированные минимальные события после разрешённого изменения. Политика уведомлений проверяет привязку получателя, настройки канала, цель, срок и подавление отправки. Адаптер передаёт только одобренный текст и безопасную ссылку. Статус доставки хранится через принятый долговременный механизм после проверки, что он готов и включён. Повторы должны быть идемпотентными и ограниченными; повторная/устаревшая доставка не должна раскрывать личные сведения.

### Что уже есть в проверенном API исходнике

В коде API на commit `4badd4d0` уже есть узкий внутренний alert sender:

- `app/service/.../alerts/TelegramAlertSender.java` вызывает Bot API `sendMessage` для одного настроенного чата и, возможно, темы форума. Использует один daemon worker, ограниченную очередь, дедупликацию в памяти и лимит в минуту. При переполнении, превышении лимита или сетевой ошибке alert теряется после предупреждения; это не durable outbox и нет долговечного журнала повторной доставки.
- `app/rest/.../ApiExceptionAdvice.java` формирует общий alert 500 из шаблона маршрута, HTTP метода, кода ошибки, класса exception и request id; текст exception и raw URI не включаются. Также считает повторяющиеся коды 503.
- `AnomalyAlertJob` и `FailedExchangeCounter` могут посылать агрегированные пороговые alerts. Некоторые сообщения содержат внутренний идентификатор компании; получатель должен быть только из числа уполномоченных сотрудников.
- `scripts/telegram-workflow-alert.sh` отправляет название workflow/job, короткий SHA коммита и ссылку на GitHub Actions run. Логи ошибок не передаются; отсутствие Telegram-уведомления не меняет итог workflow.
- `telegram-release.yml` отправляет одно best-effort сообщение о стабильном опубликованном релизе в настроенную тему группы. Документация предупреждает, что повторный запуск или timeout могут дать дубль.
- `deploy-nonprod.yml` передаёт параметры Telegram в non-production Cloud Run. В документации указана ссылка на Secret Manager token, но версия секрета и runtime grant помечены `UNKNOWN`; матрица проверок не подтверждает live-доставку. Конфигурация workflow или mocked test не доказывают, что сообщение дошло.

Это внутренние операционные/release-сценарии на обычном Bot API. В проверенном исходнике нет подтверждённого пользовательского связывания Telegram, клиентской поддержки, Telegram Business, Mini App, входящего бота или TDLib-истории. Не создавайте повторную задачу на базовый исходящий sender. Перед любым предложением проверьте актуальные CVN-521/CVN-529/CVN-550.

Для входящих действий бота проверяйте webhook secret, связь Telegram-аккаунта с пользователем/сотрудником, допустимую команду, доменные права и актуальное состояние записи. Данные callback — не подтверждение полномочий. Не превращайте webhook в альтернативный источник идентичности вместо Clerk. Детали заявки/работодателя остаются за аутентифицированным API/UI.

## События между продуктом и API

- Изменился статус заявки кандидата → нейтральное уведомление при opt-in и защищённая ссылка.
- Работодатель получил заявку или нужно действие по вакансии → сообщение только привязанному и авторизованному участнику компании.
- Превышен порог очереди поддержки/администрирования → внутренний агрегированный алерт со ссылкой на систему.
- Инцидент сервиса/ошибка доставки outbox → уведомление дежурному/менеджеру без клиентских данных и секретов.
- Приглашение, модерация, платежи или безопасность аккаунта → рассматривать отдельно; не включать без политики для каждого события.

## Технические заметки Telegram

- Bot API уже используется для внутренних service/workflow/release alerts. Для личных сообщений кандидату или работодателю отдельно нужны привязка пользователя и opt-in; бот не может первым начать личный диалог.
- Telegram Business может пригодиться поддержке, но обычный адаптер Bot API автоматически не становится Business-ботом. Проверьте нужные update/права в библиотеке и helpdesk.
- Mini App относится к UI продукта. Проверку сессии и доменных прав оставить CVNoor API; `initData` проверять по документации Telegram и не считать заменой CVNoor-авторизации.
- TDLib — библиотека пользовательского клиента, не доставки уведомлений backend. Она добавляет сеансы аккаунта, native-зависимость и риски доступа, не давая преимуществ обычной исходящей рассылке.
- Для уведомлений AI не нужен. Если его предложат для сводок/поддержки, заранее описать, какие поля передаются модели, согласие, хранение и условия провайдера.
