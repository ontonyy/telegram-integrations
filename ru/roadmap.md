# Учебный маршрут и проверка репозитория

Этот документ подводит итог недавнему изменению J10 и задаёт безопасный порядок изучения и проверки репозитория. Это план, а не утверждение, что все перечисленные проверки уже выполнены.

## Недавняя работа: восстановление после аварии при загрузке файлов J10

**Завершено в коммите `108b5fe` (`fix: recover abandoned Telegram file uploads`):**

- Активная загрузка удерживает блокировку операционной системы в своём временном каталоге — lease.
- Общая блокировка обслуживания координирует создание и очистку каталогов между процессами.
- При следующем подходящем приёме файла сервис удаляет оставшийся каталог только после получения освободившейся lease.
- Каталоги с активной блокировкой, символическими ссылками или неожиданным содержимым остаются нетронутыми.
- Целевые тесты проверяют очистку оставшегося каталога, занятую lease и неожиданные элементы. Используются синтетические файлы и поддельный Telegram gateway.
- Изменение отправлено в `origin/master`; целевой `FileIntakeServiceTest` и `git diff --check` прошли.

**Граница уже выполненной проверки:** тест занятой lease выполняется в одной JVM. Он не проверяет взаимодействие двух отдельных процессов и не доказывает поддержку блокировок всеми файловыми системами. Реальная загрузка из Telegram не выполнялась.

## Этапы изучения и проверки

### 1. Разобраться в структуре репозитория

Сначала прочитайте:

1. [Обзор репозитория](README.md)
2. [Учебный маршрут по концепциям](learning/README.md)
3. [Руководство по Java Spring примеру](examples/java-spring/README.md)
4. [Руководство по TDLib примеру](examples/tdlib-java/README.md)
5. [Описания завершённых задач](tasks/completed-issues/README.md)

В репозитории два отдельных Java-примера. Spring-пример демонстрирует бота и сервис без обязательных учётных данных. В TDLib-примере тесты на поддельном порте отделены от необязательного нативного адаптера и сценария с реальным аккаунтом.

### 2. Проследить J10 от входа до очистки

Прочитайте [J10](tasks/completed-issues/J10.md), затем изучите:

- `FileIntakeService` — проверку входных данных, жизненный цикл временного каталога, обработку текста и очистку.
- `TelegramFileGateway` и `BotApiTelegramFileGateway` — границу между логикой сервиса и файловым API Telegram.
- `FileIntakeServiceTest` и `FileIntakeWebhookTest` — тесты сервиса и webhook на синтетических данных.

Убедитесь, что можете объяснить, когда проверяются метаданные, в какой момент начинается загрузка, какие данные могут временно оказаться на диске и как выполняется очистка при успехе и ошибках.

### 3. Понять и проверить схему lease

Lease — это блокировка ОС, удерживаемая всё время загрузки. Блокировка обслуживания не позволяет другому совместимому процессу вмешаться в создание или очистку временного каталога. Решение об удалении опирается на наличие блокировки, а не на возраст файла.

Следующий шаг — добавить или запустить целевой тест с **двумя отдельными JVM-процессами**, использующими общий временный каталог: один процесс удерживает lease, пока второй начинает intake. Проверьте, что каталог первого процесса и синтетический частичный файл сохраняются. Затем смоделируйте завершение процесса и проверьте, что следующий intake удаляет оставшийся каталог. Для этого не нужны Telegram credentials или реальные файлы.

Перед использованием общего или сетевого временного каталога отдельно проверьте, что конкретная файловая система надёжно поддерживает межпроцессные блокировки Java `FileLock`. Если это не так, не полагайтесь там на этот механизм восстановления. Локальные тесты не подтверждают свойства файловой системы.

### 4. Запустить документированные проверки Java-примеров

Сборки примеров требуют Java 25.

Из корня репозитория выполните команду CI для Spring-примера:

```bash
./examples/java-spring/gradlew -p examples/java-spring clean test
```

Затем отдельно выполните тесты TDLib на поддельном порте:

```bash
./examples/java-spring/gradlew -p examples/tdlib-java test
```

CI запускает тесты Spring-примера и после доверенного push в `master` может отправить уведомление в Telegram, если настроены секреты и переменные репозитория. Тесты TDLib на поддельном порте не требуют credentials, JNI или соединения с Telegram. Сборка необязательного нативного адаптера зависит от окружения; выполняйте её по README только если этот адаптер входит в область проверки.

### 5. Безопасно проверить весь репозиторий

- Сравните `.github/workflows/java-sample-ci.yml` с локальными командами и отметьте проверки, которых нет в CI.
- Перед запуском дополнительных сценариев читайте README соответствующего примера. Не запускайте реальный вход в Telegram, загрузку или отправку сообщений и интеграции с провайдерами в рамках проверки без credentials.
- Изучите аутентификацию webhook, ограничения размера входных данных, идемпотентность, повторы исходящих вызовов, согласие пользователей, сроки хранения данных и границы авторизации в соответствующих сервисах и тестах.
- Сверяйте утверждения документации с реализацией и тестами. Тест с mock или fake adapter подтверждает локальное поведение, но не live-подключение.
- Проверьте изменённые файлы и запустите `git diff --check`. Не храните credentials, сессии аккаунтов, номера телефонов и данные клиентов в репозитории или логах.

## Когда полная локальная проверка завершена

Локальная проверка завершена, когда прошли обе документированные серии Java-тестов, тест с двумя JVM подтвердил сохранение активного каталога и восстановление после аварии, поддержка файловой системы подтверждена для планируемого хранилища, а различия между CI, документацией и кодом точно зафиксированы. Проверки с реальными аккаунтами и провайдерами выполняются отдельно и требуют собственного согласованного объёма работ и credentials.
