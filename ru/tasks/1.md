# Задача 1: завершить набор примеров Telegram на Java

## Статус

**Примеры Java без реальных credentials реализованы:** `examples/java-spring/` содержит запускаемые сценарии Java 25/Spring Boot для webhook и уведомлений Bot API, серверной проверки Mini App, группового голосования, webhook Jira/Grafana, приёма файлов с согласием, опционального AI, смоделированной Telegram Business поддержки, сбора HubSpot-контакта с согласием и внутренних заявок с проверкой роли менеджера. Отдельный [пример TDLib Java для пользовательского аккаунта](../../examples/tdlib-java/README.md) не подключён к обычному запуску Spring и требует отдельной настройки native/JNI. Живые credentials или аккаунты Telegram/HubSpot, корпоративный источник identity, внутренняя группа и данные сотрудников не использовались. Инструкции: [README Spring-примера](../../examples/java-spring/README.md) и [README TDLib](../../examples/tdlib-java/README.md).

Подробные пояснения к завершённым задачам J01–J17 собраны в [русском каталоге](completed-issues/README.md) и [английском оригинале](../../tasks/completed-issues/README.md). В каждом документе описаны результат, принцип работы, применение в проекте и граница проверки mock/live.

J16 добавляет учебный outbox на H2, переживающий перезапуск, с ограниченными повторами, `retry_after`, lease, сроком годности и очисткой. Тесты Java-примера прошли; локальный запуск demo-профиля наблюдался при выключенной отправке. Этот общий пример не проверяет и не меняет собственную доставку Telegram в CVNoor.

J17 добавляет урок по Telegram-поддержке в Chatwoot и fake-тестируемый Java-сценарий передачи оператору. Встроенный канал Chatwoot отвечает за Telegram и работу операторов; Java-шов тестируется только на заглушке и не является интеграцией с Chatwoot или CVNoor. Credentials, Telegram-сообщения и аккаунты не использовались.

Чтобы изучать примеры по понятиям, а не по номерам задач, пройдите [учебный маршрут по интеграциям Telegram](../learning/README.md) или [английскую версию](../../learning/README.md).

[J05](https://github.com/ontonyy/telegram-integrations/issues/5) реализована как Business support adapter с заглушками в [примере Java/Spring](../../examples/java-spring/README.md#telegram-business-support-intake-and-operator-handoff). Обрабатываются обновления подключения и новые/изменённые/удалённые сообщения; создаются минимальные метаданные in-memory без текста переписки; тесты проверяют передачу оператору и ограничения ответа от имени бизнеса. Business-аккаунт, диалог клиента, helpdesk и реальные отправки не использовались.

Сценарий FAQ с AI из [J11](https://github.com/ontonyy/telegram-integrations/issues/11) реализован с раскрытием обработки, отзывным согласием, отдельным подтверждением каждого запроса, только личным чатом, отменой запроса и подменяемым Claude-клиентом. Передаётся только текст, который пользователь отправил напрямую; история чата, группы, файлы, Business-сообщения и данные других пользователей в AI не передаются. Заглушки не подтверждают соответствие условиям Telegram или работу живого провайдера.

Ограниченный приём файла из [J10](https://github.com/ontonyy/telegram-integrations/issues/10) реализован. Он требует отдельного раскрытия цели и согласия в личном чате, использует временное хранилище с правами владельца и удаляет файл после подсчёта локальной статистики. Содержимое файла не отправляется AI.

[J14](https://github.com/ontonyy/telegram-integrations/issues/14) реализована как сбор заявки с mock-backed HubSpot интеграцией в [примере Java/Spring](../../examples/java-spring/README.md#consent-gated-sales-lead-capture-with-hubspot). Бот сначала раскрывает цель и получателей, затем запрашивает отдельное согласие в личном чате; в CRM передаются только введённые клиентом поля, контакт обновляется по email, назначается настроенный HubSpot owner, а менеджер получает уведомление только с CRM reference. Сделка и маркетинговая подписка не создаются; Telegram-профиль и история не копируются. Unit-тесты используют fake CRM и Telegram adapters; живые записи в CRM и отправки не выполнялись. Согласие и подавление повторных уведомлений — только in-memory состояние демо.

[J15](https://github.com/ontonyy/telegram-integrations/issues/15) реализована как сценарий приватной заявки сотрудника в [примере Java/Spring](../../examples/java-spring/README.md#private-employee-request-and-manager-approval). Роли берутся из server-side demo конфигурации; статус видит только заявитель или разрешённый менеджер; approve/reject требует отдельного callback-подтверждения от того же менеджера. Устаревшие callback отклоняются, пишется минимальный аудит с UTC-временем. Состояние хранится в памяти; корпоративная identity-система, HR/ITSM, внутренняя группа и аккаунт сотрудника не подключались.

## Пример TDLib Java для пользовательского аккаунта

В [примере TDLib](../../examples/tdlib-java/README.md) официальный JNI adapter находится в отдельном source set, вне обычного старта Spring Boot. Тесты с fake port проверяют разрешённые действия по состояниям авторизации и не требуют credentials. Необязательный live adapter использует явный ввод номера/кода/пароля; единственное действие с данными аккаунта — по команде показать до десяти названий чатов основного списка. Тела сообщений не загружаются, история не индексируется, AI не вызывается. README описывает защиту локальной БД и ключа, локальный logout, отзыв сессии в Telegram и полное удаление. Реальные credentials, native-сборка, вход в аккаунт и чтение чатов не выполнялись.

## Требования

- Код, идентификаторы и заметки для агентов писать на английском; поддерживать читательскую русскую версию.
- Не коммитить токен бота, API ID/hash, телефон, код входа, TDLib-сеанс/БД, сообщения пользователя и секреты провайдера.
- Получать секреты из переменных окружения или secret manager. Не добавлять заполненный `.env`.
- Проверять права и данные на сервере; действия ограничивать явным списком.
- При локальной разработке не отправлять реальные сообщения Telegram и не подключать аккаунт без отдельного запроса.
- До AI-обработки данных Telegram повторно проверить условия Telegram, согласие для конкретного контекста, хранение у провайдера и требования приватности. Для J11 условия Telegram API, лицензия на контент, условия Bot Developer и сведения о хранении Anthropic API проверены 2026-11-15; перед запуском проверку нужно повторить.
- Объяснить границы локальных и смоделированных примеров: они не подтверждают работу живой интеграции.

## Критерии завершения

- Добавить отдельные инструкции для TDLib и приёма файлов: требования, запуск, удаление и область доступных данных. **Готово:** [README TDLib Java](../../examples/tdlib-java/README.md) и [README Java/Spring](../../examples/java-spring/README.md).
- Сохранить возможность компиляции существующего примера без учётных данных.
- Перед коммитом проверить отслеживаемые файлы на секреты и выполнить `git diff --check`.
