# J16 — Доставка уведомлений Telegram через постоянный outbox

[English](../../../tasks/completed-issues/J16.md) · [GitHub issue #16](https://github.com/ontonyy/telegram-integrations/issues/16)

## Что сделано

В примере Java/Spring появился H2 outbox в файле, worker с временной блокировкой lease, защита от повторной постановки события, срок годности и очистка завершённых записей. Отправитель Telegram классифицирует flood control и ошибки клиента; worker учитывает `retry_after` и ограниченные экспоненциальные повторы временных ошибок. Расписание worker и реальные отправки выключены по умолчанию.

## Как это работает

Приложение записывает событие со стабильным event ID. Worker выбирает готовую запись и ставит lease, чтобы параллельный worker не взял её одновременно. Номер попытки одновременно служит fencing-значением: если lease истёк и запись забрал другой worker, первый уже не сможет перезаписать состояние второго. После успешного ответа Bot API запись получает состояние `SENT`. Для HTTP 429 используется Telegram `retry_after`; HTTP 5xx и неоднозначные сбои сети допускают повтор; остальные ответы 4xx считаются постоянной ошибкой. Число попыток, возраст сообщения и срок хранения завершённых записей ограничены настройками.

Worker запускается только при одновременных `TELEGRAM_SEND_ENABLED=true` и `TELEGRAM_OUTBOX_WORKER_ENABLED=true`. По умолчанию локальная H2 база — файл в временной папке ОС, он сохраняется при перезапуске приложения. Тесты используют отдельные H2 базы и fake/local HTTP; запросов к Telegram нет.

## Применение в реальном проекте

Записывайте outbox в той же транзакции базы данных, что и бизнес-изменение, которое требует уведомления. Worker может жить в том же приложении или отдельном сервисе, выбирать готовые записи и вызывать Telegram. Согласие получателя, права, локализация и минимизация данных должны проверяться до постановки уведомления. Храните только нужный для доставки минимум, ограничьте доступ к базе и определите срок удаления.

Outbox сохраняет намерение отправить сообщение и состояние повторов, но не гарантирует отправку ровно один раз. Telegram может принять сообщение, а ответ потеряться; повтор тогда способен создать дубликат. Используйте стабильный ID бизнес-события для защиты от повторной логической постановки и проектируйте уведомления с учётом возможных дубликатов.

## Код и границы

См. [`JdbcNotificationOutbox`](../../../examples/java-spring/src/main/java/example/telegram/JdbcNotificationOutbox.java), [`NotificationOutboxDispatcher`](../../../examples/java-spring/src/main/java/example/telegram/NotificationOutboxDispatcher.java), [`NotificationOutboxPolicy`](../../../examples/java-spring/src/main/java/example/telegram/NotificationOutboxPolicy.java), [`TelegramBotClient`](../../../examples/java-spring/src/main/java/example/telegram/TelegramBotClient.java) и [тесты outbox](../../../examples/java-spring/src/test/java/example/telegram/JdbcNotificationOutboxTest.java).

В демо используется H2; это учебный адаптер, а не заявление о production-готовности PostgreSQL. Для выбранной БД нужно адаптировать идемпотентный insert, границы транзакции, пул соединений, метрики, alerting, хранение и обслуживание базы. Настройте lease длиннее HTTP timeout отправителя или добавьте продление lease для долгих операций. Просроченный lease упавшего worker можно повторно получить; если предыдущая попытка уже дошла до Telegram, повтор может отправить дубль.

**Проверка:** тесты Java-примера прошли с H2 и mock/local HTTP. Spring-приложение также локально запустилось с demo-профилем и выключенной отправкой Telegram. Реальные токен, chat ID, отправка Telegram и production БД не использовались. Поле Telegram `retry_after` сверено с [документацией ResponseParameters Bot API](https://core.telegram.org/bots/api#responseparameters) 2026-11-15.
