# J03 — Protect the Spring webhook and handle duplicate updates

[Русская версия](../../ru/tasks/completed-issues/J03.md) · [GitHub issue #3](https://github.com/ontonyy/telegram-integrations/issues/3)

## What was delivered

The Telegram webhook checks its shared-secret header, validates the update ID, routes supported message/callback shapes, and uses an idempotency seam before applying side effects.

## How it works

`POST /telegram/webhook` rejects an unset secret outside the explicit demo profile and compares supplied and configured secrets in constant time. `TelegramUpdateRegistry` records processed `update_id` values; the sample implementation is bounded in-memory state. A failed handler returns a retryable service error, while a repeated completed update does not repeat the same side effect.

Run the controller tests:

```bash
./examples/java-spring/gradlew -p examples/java-spring test --tests example.telegram.TelegramWebhookControllerTest
```

## Use this in a real project

Register an HTTPS webhook with Telegram's `secret_token`, set the same secret in a secret manager, and subscribe only to the update types you handle. Enforce request-size and rate limits at the edge. Replace the local registry with a durable, shared idempotency store before running multiple instances.

## Implementation and limits

See [`TelegramWebhookController`](../../examples/java-spring/src/main/java/example/telegram/TelegramWebhookController.java), [`TelegramUpdateRegistry`](../../examples/java-spring/src/main/java/example/telegram/TelegramUpdateRegistry.java), and the [webhook tests](../../examples/java-spring/src/test/java/example/telegram/TelegramWebhookControllerTest.java). The demo registry clears on restart and cannot guarantee exactly-once delivery across Telegram and external services.
