# J19 — Simulate Telegram Stars payment and refund lifecycle

[Русская версия](../../ru/tasks/completed-issues/J19.md) · [GitHub issue #19](https://github.com/ontonyy/telegram-integrations/issues/19) · [Learning lesson](../../learning/09-stars-payments.md)

## What changed

The Spring example now routes synthetic `/buy-demo`, `/paysupport`, pre-checkout, successful-payment, and `/refund-demo` events through `TelegramStarsPaymentService`. The service validates ownership, `XTR`, the expected amount, order expiry, and checkout state. It fulfills only after a valid `successful_payment`, records charge IDs to avoid duplicate fulfillment, and only permits the buyer to request a refund. A confirmed refund is not repeated; an ambiguous result is marked `REFUND_UNKNOWN` for manual reconciliation.

`TelegramStarsGateway` is an adapter seam. The only Spring implementation is `SimulatedTelegramStarsGateway`, an in-memory fake that does not call Telegram or move Stars. `/buy-demo` creates an order intent only; the app does not call `sendInvoice`. Unit and webhook tests submit synthetic update data.

## Verification and limits

Focused tests: `./gradlew test --tests example.telegram.TelegramStarsPaymentServiceTest --tests example.telegram.TelegramWebhookControllerTest` from `examples/java-spring/`.

State and update idempotency are bounded process-local memory, lost on restart and not shared across instances. The ten-second response budget is checked against an injected local clock; tests do not measure the Telegram network deadline. There is no real order, product delivery, invoice, payment, refund, or support provider connection.

Official behavior: [Telegram Stars payments](https://core.telegram.org/bots/payments-stars), [Bot API `answerPreCheckoutQuery`](https://core.telegram.org/bots/api#answerprecheckoutquery), and [Bot API `refundStarPayment`](https://core.telegram.org/bots/api#refundstarpayment).
