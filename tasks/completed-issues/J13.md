# J13 — Review Telegram-to-Codex and Claude Code bridges

[Русская версия](../../ru/tasks/completed-issues/J13.md) · [GitHub issue #13](https://github.com/ontonyy/telegram-integrations/issues/13)

## What was delivered

The research compares Telegram-to-agent projects and distinguishes full applications from bridges, libraries, and prototypes. It records documented features separately from source-reviewed behavior and from runtime verification.

## How the decision works

The review covers supported agent/OS combinations, DM/group behavior, where code runs, identity controls, approvals/sandboxing, and storage of tokens or sessions. The recorded decision is **not to add a generic Java Telegram-to-agent bridge now**. The sources reviewed do not justify another adapter, and safe agent access requires stronger repository isolation and authorization than a bot mention or group membership.

## Use this in a real project

If phone control is the goal, start with the agent's official remote or channel option where available. For a custom system, begin with a narrow status/test/patch-preparation pilot in a dedicated OS account and isolated checkout; require explicit approvals before write or shell actions. Never put a coding agent with an unrestricted working repository behind a group bot.

## Implementation and limits

See the [implementation landscape](../../02-research/implementation-landscape.md) and its [research index](../../02-research/README.md). This issue produced research and a no-build decision, not a running Telegram bridge. Candidate projects were not installed, connected, or tested with real accounts or repositories.
