# J17 — Demonstrate Chatwoot Telegram customer support

[Russian version](../../ru/tasks/completed-issues/J17.md) · [GitHub issue #17](https://github.com/ontonyy/telegram-integrations/issues/17) · [Learning lesson](../../learning/08-chatwoot-support.md)

## What was delivered

The new lesson covers Chatwoot's built-in Telegram Bot API inbox and its documented Telegram Business bot support, including setup, sender identity, business rights, the Business 24-hour window, operator handoff, conversation history, stored data, and a proposed owner-gated CVNoor use.

The Java sample adds [`ChatwootSupportHandoff`](../../examples/java-spring/src/main/java/example/telegram/ChatwootSupportHandoff.java), a deliberately small application-side choreography seam. Its tests use a synthetic incoming customer message, conversation/operator IDs and a recording fake to demonstrate intake, assignment and an assigned-operator reply request, while rejecting an unauthorized operator and invalid/unassigned replies. The Java side keeps only a conversation reference; Chatwoot remains the message system of record.

## What owns what

Chatwoot's built-in Telegram channel registers and consumes the Telegram webhook, maps Telegram updates to Chatwoot contacts and conversations, stores the message history/attachments, provides assignment and the operator UI, and sends replies back through Telegram. A standard bot reply is sent by the bot identity; the Chatwoot agent is the human author recorded in the helpdesk, not the Telegram sender. In Business mode, Telegram supplies a business connection ID; the connection owner selects eligible chats and grants bot rights, and `can_reply` permits sending/editing in private chats with customer activity during Telegram's rolling 24-hour window. That 24-hour condition is specific to the Business bot flow, not a universal Bot API rule. Business replies are sent on behalf of the connected business account, not the agent's personal Telegram account.

The Java seam does not replace any of that. It has no Telegram or Chatwoot HTTP implementation, webhook endpoint/signature validation, database, credentials, or live configuration. In the normal human-support setup, agents can assign and reply entirely inside Chatwoot without this Java code. The lesson names environment-variable placeholders for any separately approved future API connection; no secret values were added.

Chatwoot stores customer/contact references, conversation and message records including text and sender/metadata, and attachment records/files. The current Telegram channel source stores a bot token and conditionally encrypts it when Chatwoot encryption is configured. Retention, deletion, backup, access, and attachment storage therefore need decisions for the chosen Chatwoot deployment. Stored conversation history is only what Chatwoot received and retained, not a Telegram account-wide archive or proof of historical backfill.

## CVNoor boundary

The pattern may inform a **proposed, owner-gated** support pilot. It does not implement, connect, or verify support delivery in CVNoor. J16's local H2 outbox remains a teaching example and is unrelated to CVNoor delivery.

## Verification boundary

The focused Java tests exercise a fake gateway with synthetic values. They do not contact Telegram or Chatwoot. Live verification is still needed for inbox creation, webhook delivery, assignments, message sender identity, Business rights/window enforcement, media, deletion and retention on the actual Chatwoot deployment. Current official Chatwoot documentation and source and Telegram Bot API references were checked on 2026-11-15; see the [lesson's source links](../../learning/08-chatwoot-support.md).
