# J18 — Shared group Mini App with server authorization and concurrency

[Русская версия](../../ru/tasks/completed-issues/J18.md) · [GitHub issue #18](https://github.com/ontonyy/telegram-integrations/issues/18) · [Learning lesson](../../learning/04-mini-apps.md)

## What was delivered

The Java/Spring Mini App page now includes a synthetic shared availability board alongside J07's owner-scoped request form. It uses the signed launch user's Telegram ID for the participant's own contribution and signed `chat_instance` as the board context. Shared responses expose aggregate counts per slot and the caller's own selected slots; they do not expose other participants' Telegram IDs or individual choices.

## Authorization and update behavior

`SharedMiniAppController` verifies raw `initData` with `TelegramInitDataValidator`, requires a user plus `chat_instance` and group/supergroup `chat_type`, and then calls `SharedMiniAppAuthorizer`. The configured implementation requires an exact pair from `TELEGRAM_MINIAPP_SHARED_ALLOWED_MEMBERSHIPS`, written as comma-separated `chat_instance=user_id` values. Empty configuration denies all requests. A signed context is not group membership proof; the allowlist is an application demo policy.

`SharedAvailabilityBoardService` stores one contribution per signed user in a board keyed by `chat_instance`. An update applies only if the submitted version matches the current board version. A successful write increments the version; a stale write returns HTTP 409 with current aggregate state so the client can review and retry. An identical retry is a no-op even if it repeats the old expected version. Contribution validation completes before any board state changes.

## Use in a real project

Use direct-link Mini Apps for collaborative views that need a richer interface than chat messages or buttons. Treat signed launch identity, Telegram chat context, and the application's own permissions as separate inputs. Define enrollment, roles, retention and user-visible disclosure in the application. Use durable shared storage and an atomic compare-and-set/database transaction when multiple instances can serve the board.

## Implementation and limits

See [`SharedMiniAppController`](../../examples/java-spring/src/main/java/example/telegram/SharedMiniAppController.java), [`ConfiguredSharedMiniAppAuthorizer`](../../examples/java-spring/src/main/java/example/telegram/ConfiguredSharedMiniAppAuthorizer.java), [`SharedAvailabilityBoardService`](../../examples/java-spring/src/main/java/example/telegram/SharedAvailabilityBoardService.java), [controller tests](../../examples/java-spring/src/test/java/example/telegram/SharedMiniAppControllerTest.java), and [service tests](../../examples/java-spring/src/test/java/example/telegram/SharedAvailabilityBoardServiceTest.java).

The in-memory store holds at most 500 boards, 50 contributors per board, and eight slots per contribution. It loses all state at restart and coordinates only within one JVM. The allowlist is configuration for a teaching example, not a live Telegram group membership directory. Telegram does not provide the Mini App with group message history or permission to send as a user.

**Verification:** tests use synthetic user IDs, chat contexts, and signed launch data. No Telegram account, public Mini App URL, group, or message was used. Local tests do not prove live Mini App launch behavior or cross-instance database concurrency.
