# J16 — Deliver Telegram notifications through a durable outbox

[Русская версия](../../ru/tasks/completed-issues/J16.md) · [GitHub issue #16](https://github.com/ontonyy/telegram-integrations/issues/16)

## What was delivered

The Java/Spring sample now has a file-backed H2 outbox, a delivery worker with leased claims, duplicate-event protection, expiry and terminal-record cleanup. The Telegram sender classifies flood-control and client errors; the worker honors `retry_after` and uses bounded exponential retry for transient failures. Both the worker schedule and Telegram sending are off by default.

## How it works

The application inserts an event using a stable event ID. A worker claims one due row and sets a lease so another worker cannot claim it at the same time. The attempt number is also a fencing value: if the lease expires and a second worker reclaims the row, the first worker can no longer overwrite the second worker's state. On a successful Bot API response it marks the row `SENT`. HTTP 429 uses Telegram's `retry_after`; HTTP 5xx and ambiguous transport failures are retryable; other 4xx responses are permanent. Attempts, message age, and terminal retention are bounded by configuration.

The worker can be enabled only with both `TELEGRAM_SEND_ENABLED=true` and `TELEGRAM_OUTBOX_WORKER_ENABLED=true`. The local H2 database defaults to a file under the OS temporary directory and survives app restarts. Tests use isolated H2 databases and fake/local HTTP; they do not call Telegram.

## Use this in a real project

Insert the outbox row in the same database transaction as the business change that requires a notification. A worker in the same or a separate service can claim due rows and call Telegram. Keep recipient opt-in, authorization, localization, and message minimization in the application policy before enqueueing. Store only the minimum content needed to deliver, restrict database access, and set a retention policy.

The outbox makes enqueueing and retry state durable, but it cannot make Telegram delivery exactly-once. Telegram may accept a send while the response is lost; retrying that ambiguous request can create a duplicate. Use stable business event IDs to prevent duplicate logical enqueueing, and design notifications to tolerate duplicates.

## Implementation and limits

See [`JdbcNotificationOutbox`](../../examples/java-spring/src/main/java/example/telegram/JdbcNotificationOutbox.java), [`NotificationOutboxDispatcher`](../../examples/java-spring/src/main/java/example/telegram/NotificationOutboxDispatcher.java), [`NotificationOutboxPolicy`](../../examples/java-spring/src/main/java/example/telegram/NotificationOutboxPolicy.java), [`TelegramBotClient`](../../examples/java-spring/src/main/java/example/telegram/TelegramBotClient.java), and [outbox tests](../../examples/java-spring/src/test/java/example/telegram/JdbcNotificationOutboxTest.java).

The demo uses H2 and is a teaching adapter, not a claim of PostgreSQL production hardening. Adapt idempotent insert syntax, transaction boundaries, pooling, metrics, alerting, retention, and database operations to your chosen database. Set the lease longer than the sender's HTTP timeout, or add lease renewal for longer operations. A crashed worker's expired lease can be reclaimed; if the previous attempt reached Telegram before the crash, that retry may duplicate the message.

**Verification:** the Java sample test suite passed with H2 and mock/local HTTP. The demo-profile Spring app also started locally with Telegram sending disabled. No real token, chat ID, Telegram send, or production database was used. Telegram's `retry_after` field was checked against the [Bot API ResponseParameters documentation](https://core.telegram.org/bots/api#responseparameters) on 2026-11-15.
