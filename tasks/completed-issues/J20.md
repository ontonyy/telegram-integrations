# J20 — Add Telegram Login OIDC to a Java website

[Русская версия](../../ru/tasks/completed-issues/J20.md) · [GitHub issue #20](https://github.com/ontonyy/telegram-integrations/issues/20) · [Learning lesson](../../learning/10-telegram-login-oidc.md)

## What changed

The Java/Spring sample now has an optional Telegram Login OIDC flow backed by Spring Security. It uses the standard authorization-code callback, requires PKCE S256, keeps client credentials on the server, and defaults to the `openid` scope. `/login-demo/me` returns only the verified OIDC subject and grants no application roles. It is separate from the Mini App `Telegram.WebApp.initData` HMAC validator.

The feature is disabled by default. An enabled configuration performs OIDC discovery using the configured issuer, with Telegram's issuer as the default. The fake issuer tests exercise authorization redirect and callback using synthetic RSA keys and values. They cover PKCE and redirect URI binding, callback state, ID-token nonce, signature, issuer, audience, expiry, minimal scope, and a subject-only response. The fake discovery document has no UserInfo endpoint, matching Telegram's documented boundary.

## Verification and limits

Focused test: `./gradlew test --tests example.telegram.TelegramLoginOidcSecurityTest` from `examples/java-spring/`.

The feature uses a server-side HTTP session. Session storage/sharing, cookie policy, account linking, application authorization, logout, and production deployment hardening are outside this demo. Tests use only a loopback mock issuer; no Telegram client registration, credentials, profile, or live login was used. Optional profile, phone, and bot-access scopes are not requested by default.

Official behavior: [Telegram Login OIDC](https://core.telegram.org/bots/telegram-login), [Spring Security OAuth2 Login](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/), and [Spring Boot OAuth2 client configuration](https://docs.spring.io/spring-boot/reference/security/oauth2.html).
