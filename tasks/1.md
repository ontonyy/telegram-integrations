# Task 1: Complete the Java Telegram example set

## Status

**Planned credential-free examples implemented:** `examples/java-spring/` contains runnable Java 25/Spring Boot examples for a dry-run Bot API webhook, an owner-scoped Mini App request flow, consent-based private text-file intake, and an optional AI flow for directly submitted private-chat prompts with per-question confirmation. The standalone [TDLib Java account-client example](../examples/tdlib-java/README.md) is separate from normal Spring startup and requires an explicit manual setup for native/JNI use. No live Telegram credentials or account were used. See the [Spring README](../examples/java-spring/README.md) and [TDLib README](../examples/tdlib-java/README.md).

[J05](https://github.com/ontonyy/telegram-integrations/issues/5) is implemented as a mock-backed Business support adapter in the [Java/Spring sample](../examples/java-spring/README.md#telegram-business-support-intake-and-operator-handoff). It processes connection and new/edit/delete update shapes, creates minimal in-memory ticket metadata without retaining message text, and tests operator takeover plus guarded business-scoped replies. No Business account, customer conversation, helpdesk or live Telegram message was used.

The direct-to-bot FAQ example in [J11](https://github.com/ontonyy/telegram-integrations/issues/11) is implemented with an explicit disclosure, volatile feature consent, one confirmation per exact question, private-chat-only routing, cancellation/revocation, a mockable Claude client, and a transparent but unconnected human-handoff marker. The sample never sends chat history, group messages, files, Business messages, or other users’ content to AI. Local mocks do not establish Telegram policy compliance or live provider behavior.

The bounded file-intake example in [J10](https://github.com/ontonyy/telegram-integrations/issues/10) is implemented. It requires explicit private-chat disclosure and consent, stores files only in owner-restricted temporary storage, and deletes them after local text statistics are calculated. The example does not send file content to AI.

[J14](https://github.com/ontonyy/telegram-integrations/issues/14) is implemented as a mock-backed HubSpot lead-capture path in the [Java/Spring sample](../examples/java-spring/README.md#consent-gated-sales-lead-capture-with-hubspot). It asks for disclosure and separate consent in a private chat, accepts only fields typed by the customer, upserts the CRM contact by email, assigns a configured HubSpot owner, and routes a manager notification with only the CRM reference. It does not create deals, grant marketing consent, or copy Telegram profile/history. Unit tests use fake CRM and Telegram adapters; no live CRM write or Telegram send was performed. Consent and notification deduplication are in-memory demo state, not production guarantees.

[J15](https://github.com/ontonyy/telegram-integrations/issues/15) is implemented as a credential-free private employee request flow in the [Java/Spring sample](../examples/java-spring/README.md#private-employee-request-and-manager-approval). Roles resolve from server-side demo configuration, request status is visible only to its requester or an authorized manager, and approve/reject requires a second callback confirmation by the same manager. Stale callbacks are rejected; only a minimal UTC audit is recorded. State is in-memory and no company identity source, HR/ITSM, internal group or employee account was connected.

## TDLib Java account-client example

The [TDLib example](../examples/tdlib-java/README.md) keeps its official JNI adapter in a separate source set and away from the normal Spring Boot application. Credential-free tests use a fake port to check authorization-state action guards. The optional live adapter handles user-driven phone/code/password entry and exposes one explicit local operation to list up to ten main-list chat titles. It does not load message bodies, index history or call AI. The README documents local database/key protection, local logout, Telegram device revocation and deletion. No real credentials, native library build, account authorization or chat read were used.
